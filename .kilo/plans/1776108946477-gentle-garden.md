# RBAC Fix Plan: Restrict Client Access to Menus

## Problem Summary
Clients can access and view menus that should only be visible to admins and lawyers. The sidebar displays all navigation items (Cases, Tasks, Documents, Billing, Trust Accounts, Calendar, CRM, Reports, Search, Notifications) to all authenticated users, violating role-based access control requirements.

## Current State Analysis
- **Role System**: Uses string-based roles (admin, attorney, paralegal, client, billing_manager) stored in users.role column
- **Menu Location**: All menus defined in `resources/views/layouts/sidebar.blade.php` without role restrictions
- **Route Protection**: Most routes use only 'auth' middleware, lacking role-based restrictions
- **Controller Authorization**: CaseController has some authorization, but others (Tasks, Documents, Billing) lack user-specific filtering
- **Blade Restrictions**: Limited use of @can directives; most content visible to all users
- **Inconsistency**: Role models exist but underutilized; mix of string roles and potential relationship-based system

## Root Causes
1. Sidebar renders all menus unconditionally for authenticated users
2. Missing role middleware on route groups
3. Controllers don't filter data by user role/ownership
4. Underutilization of existing Policy system

## Proposed Solution
Implement comprehensive RBAC by:
- Adding role-based visibility logic to sidebar menu
- Applying appropriate role middleware to route groups
- Adding authorization checks and data filtering in controllers
- Standardizing role checking methods across the application

## Implementation Steps

### Phase 1: Menu Visibility Restrictions
1. **Update sidebar.blade.php**: Add @if conditions around menu items based on user roles:
   - Admin-only: Management, Reports (admin features)
   - Admin/Lawyer: Cases, Tasks, Documents, Billing, Trust Accounts, Calendar, CRM
   - All authenticated: Dashboard, Search, Notifications

2. **Define Role Checking Helpers**: Ensure consistent role checking methods in User model

### Phase 2: Route-Level Protection
1. **Add Role Middleware to Routes**: Update web.php and api.php to include role middleware:
   - Admin routes: `middleware(['auth', 'role:admin'])`
   - Lawyer routes: `middleware(['auth', 'role:attorney'])`
   - Client routes: `middleware(['auth', 'role:client'])`

2. **Group Routes Logically**: Organize routes by required role access

### Phase 3: Controller Authorization
1. **Add Policy Checks**: Implement $this->authorize() calls in all controller methods
2. **User-Specific Filtering**: Modify index methods to filter data based on user role:
   - Clients: Only see their own cases/tasks/documents
   - Lawyers: See assigned cases plus general access
   - Admins: See all data

3. **Create Missing Policies**: Add Policies for Tasks, Documents, Billing, etc.

### Phase 4: Blade Template Updates
1. **Add @can Directives**: Update blade templates to conditionally show content/actions
2. **Role-Based UI Elements**: Hide/show buttons, links, and sections based on permissions

### Phase 5: Testing and Verification
1. **Role Testing**: Test each role's access to menus and functionality
2. **Data Isolation**: Verify clients can't access other users' data
3. **UI Consistency**: Ensure menus hide/show correctly across all pages

## Verification Criteria
- Clients see only: Dashboard, their Cases, their Documents, Search, Notifications
- Lawyers see: All client menus plus Management, Reports (limited)
- Admins see: All menus including admin-only sections
- Routes properly redirect unauthorized users
- Database queries filter data by user ownership/role

## Potential Challenges
- Existing data relationships may need updates for proper filtering
- Blade template changes may affect multiple views
- Role middleware hierarchy needs careful configuration
- Performance impact of additional authorization checks

## Rollback Plan
- Keep backup of original sidebar.blade.php
- Test incrementally, one menu section at a time
- Use feature flags if available to toggle changes
